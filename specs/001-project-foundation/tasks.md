## Task Format & Conventions

- Each task begins with a Markdown checkbox and a sequential Task ID (`T001`–`T051`).
- `[P]` means the task can run in parallel after all listed dependencies are complete and provided it does not modify files concurrently with another task.
- `[US1]`–`[US6]` maps the task to its parent User Story.
- Every task identifies target paths, requirement references, dependencies, and testable acceptance criteria.
- Tests are mandatory deliverables. Unit tests must not require Docker; integration tests may require the declared local infrastructure; benchmarks are opt-in and are not part of the default deterministic verification run.
- Do not add authentication, RBAC, database connectors, metadata extraction, catalog features, or AI functionality in this foundation feature.
- Do not silently change a requirement or an architectural decision in `spec.md`, `plan.md`, or the Constitution. If a conflict is discovered, stop the affected task, document the conflict, and request a decision rather than inventing a new baseline.

## Phase 6: User Story 4 — Operator Health & Readiness Probes (P2)

**Goal**: Provide separate liveness and readiness probes with bounded concurrency, driver-level timeouts, and safe recovery.

**Independent Test**: Verify liveness without datastore access; verify healthy readiness; then interrupt PostgreSQL or Redis and verify a sanitized HTTP 503 within the specified failure-detection target. Run saturation and recovery tests.

- [ ] T026 [P] [US4] Implement Pydantic health response models.

    2. Field names, types, enum values, and optionality match the contract exactly.

    4. Contract validation tests cover valid and invalid payloads.

- [ ] T027 [US4] Implement a Redis client factory with explicit network timeouts.
  - **Target**: `backend/app/core/redis.py`
  - **Requirement**: FR-010
  - **Dependencies**: T006
  - **Acceptance Criteria**:
    1. Builds the Redis client from centralized settings.
    2. Sets `socket_connect_timeout=2.0`, `socket_timeout=2.0`, and `retry_on_timeout=False`.
    3. Exposes a dependency/provider suitable for application lifespan management and tests.
    4. Does not log or expose the Redis URL or credentials.

- [ ] T028 [US4] Implement bounded readiness-probe admission control and executor lifecycle.
  - **Target**: `backend/app/api/routes/health.py`, `backend/app/core/health_probe.py` (if separated)
  - **Requirement**: FR-009, FR-010, NFR-004
  - **Dependencies**: T010, T026, T027
  - **Acceptance Criteria**:
    1. Uses a dedicated `ThreadPoolExecutor(max_workers=4)` per API process for blocking PostgreSQL and Redis probes.
    2. A readiness request acquires exactly one admission permit before submitting any blocking work.
    3. Per-process admission capacity is two concurrent readiness requests; saturation returns HTTP 503 immediately and submits no queued work.
    4. The two datastore checks for an admitted request execute concurrently.
    5. The permit is released only after both underlying blocking operations have actually completed, not merely when the HTTP coroutine is cancelled or the client disconnects.
    6. Completion callbacks release capacity safely on the owning event loop (for example, using `loop.call_soon_threadsafe` where callbacks execute on worker threads).
    7. Release is idempotent and occurs exactly once across success, exception, cancellation, and shutdown paths.
    8. Client cancellation does not falsely free capacity while a blocking thread is still running.
    9. Executor shutdown is integrated into application lifespan and respects bounded driver timeouts.
    10. The documented production capacity is two concurrent readiness requests per API process, or eight across four API processes.
    11. The implementation does not rely on `asyncio.wait_for` to terminate a blocking thread.
    12. Tests cover permit acquisition, saturation, completion, cancellation, and exactly-once release.

- [ ] T029 [US4] Implement `GET /health/live`.
  - **Target**: `backend/app/api/routes/health.py`
  - **Requirement**: FR-009, NFR-004, Contract `health-api.json`
  - **Dependencies**: T028
  - **Acceptance Criteria**:
    1. Returns HTTP 200 and the exact liveness response defined by `health-api.json` while the process can serve requests.
    2. Does not access PostgreSQL or Redis.
    3. Does not acquire a readiness admission permit.
    4. Local measured response time is `<5ms` under the defined benchmark conditions.

- [ ] T030 [US4] Implement `GET /health/ready` with concurrent PostgreSQL and Redis checks.
  - **Target**: `backend/app/api/routes/health.py`, `backend/app/core/health_probe.py`
  - **Requirement**: FR-010, NFR-003, NFR-004, SC-003, Contract `health-api.json`
  - **Dependencies**: T027, T028, T029
  - **Acceptance Criteria**:
    1. Acquires admission capacity before submitting work; saturated requests return the documented HTTP 503 response without executor submission.
    2. Executes PostgreSQL `SELECT 1` and Redis `PING` concurrently in the dedicated executor.
    3. PostgreSQL connection establishment uses `connect_timeout=2`; this setting is not treated as a query execution timeout.
    4. The readiness query uses a server-side PostgreSQL `statement_timeout=2000` for the probe operation.
    5. Redis uses `socket_connect_timeout=2.0`, `socket_timeout=2.0`, and `retry_on_timeout=False`.
    6. Returns HTTP 200 with `status="ready"` only when both checks succeed.
    7. Returns HTTP 503 with `status="unhealthy"` when either dependency fails; error details are sanitized and do not include credentials, raw connection URLs, or internal stack traces.
    8. The warm local healthy-path target is P95 `<25ms`, and in all cases the endpoint remains within the specified local `<50ms` healthy response requirement under the benchmark environment.
    9. Failure detection is measured against the SC-003 target of two seconds for the specified intentional datastore-disconnect scenarios. Do not claim a universal hard two-second bound based only on socket timeout settings; validate connection failure, stalled query, event-loop scheduling, and response overhead experimentally.
    10. If the measured failure-detection target cannot be met, document the evidence and raise a spec/plan decision before weakening the acceptance criterion.

## Dependencies & Execution Order

### Phase flow

Phase 1 tasks establish the repository and toolchain. Phase 2 tasks establish shared foundations. After the relevant prerequisites in Phase 2 are complete, User Stories 1–6 may proceed in parallel where their file ownership and dependencies permit. Phase 9 verification is performed only after the artifacts it verifies are complete.

```text
T001
 ├─ Phase 1: T002, T003, T004, T005 (parallel after T001)
 └─ Phase 2: T006–T016 (each follows its explicit task dependencies)

       ├─ US5: T037 + T038; T040 → T041; then T039
       └─ US6: T042 + T043 + T044 + T045 → T046 → T047
                                      │
Phase 9: T048, T049, T050, T051 after their listed prerequisites
```

### Critical dependency notes

1. `T001` is the repository prerequisite for all work.
2. `T003`, `T004`, and `T005` are independent setup tasks after `T001`.
3. `T006` is the centralized configuration prerequisite for backend services.
4. `T009 → T013 → T017` is the ordered edit chain for `backend/app/main.py`.
5. `T010 → T011` establishes database session management; `T010 → T012 → T020 → T021` establishes migrations.
6. `T014` establishes backend test conventions and fixtures; it does not mean every test must use a live datastore.
7. `T028 → T029 → T030` is the ordered health-route implementation chain. `T031` is unit coverage; `T032` and `T033` are integration/specialized tests.
8. `T044` and `T045` can proceed independently after their respective prerequisites; both are required before `T046`, which is required before `T047` and `T050`.
9. `T047` must package both container images and dependency assets. `T049` verifies host-side offline installation/build/test; `T050` verifies image-only production deployment.

### Shared-file conflict chains

- `backend/app/main.py`: `T009` → `T013` → `T017`.
- `backend/app/api/routes/health.py`: `T028` → `T029` → `T030`.

- Phase 1: `T002`, `T003`, `T004`, and `T005` can run in parallel after `T001`.
